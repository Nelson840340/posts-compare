# 帖子相似度检测系统设计文档

- 日期：2026-08-23
- 状态：已评审通过（brainstorming 六节设计逐节确认）
- 技术方案：方案 A —— CLIP ViT-B/32 + multilingual-e5-small + Faiss 单机检索 + FastAPI/SQLite

---

## 1. 背景与目标

每月新发布约 30 万帖子，存在大量重复发帖：同一图片发多帖、图片裁剪后重发、文字相同或高度相似。目标是降低相似帖子的推送权重。

**本期交付功能**：新增一个帖子（图片 + 文字），返回该帖子与**最近 30 天所有帖子**的最大相似度，供下游推荐系统降权使用。

## 2. 需求摘要（已确认）

| 维度 | 结论 |
|---|---|
| 时效 | 准实时异步：业务方接口推帖 → 后台数秒内计算 → 结果落库可查 |
| 相似度语义 | `max_sim = max(图片相似度, 文字相似度)`，任一信号命中即视为相似 |
| 内容形态 | Demo 简化为 1 张图 + 1 段正文（无标题）；`image_*` 字段设计为未来可转可选（支持纯文字帖），接口无破坏性变更 |
| 规模 | Demo：万级以内帖子，单机；设计按生产目标 30 万帖/30 天窗口（30 万/月 ≈ 窗口存量 30 万）演进 |
| 算力 | CPU 优先（AMD 7900 XTX ROCm 仅作可选加速开关），中英双语内容 |
| 基建 | 全新绿色项目，无既有 MQ/向量库；生产数据源为 MongoDB，Demo 用 SQLite |
| 关键难点 | 图片**裁剪后重发**仍需识别（感知哈希 pHash/dHash 对裁剪脆弱，故弃用） |
| 不做作者排除 | 同用户重复发帖正是要抓的目标；下游如需排除凭 post_id 自行关联 |

## 3. 总体架构

### 3.1 部署形态

单进程单机的 FastAPI 应用，进程内 asyncio 任务队列实现准实时异步。所有组件同进程，但模块间以协议接口隔离，生产化时按边界替换，核心逻辑零改动。

### 3.2 组件结构

```
业务方                        FastAPI 单进程（Demo）/ 多副本（生产）
  │ POST /posts          ┌──────────────────────────────────────────┐
  ▼                      │  API 层        收帖→入队→202；查询相似度结果 │
FastAPI ──入队──▶        │      │                                    │
  ▲                      │      ▼ asyncio.Queue（有界）              │
  │ GET /posts/{id}/sim  │  后台 Worker   串行消费                     │
  │                      │      ├─ Embedder     CLIP 图(512d)+e5 文(384d)│
  │                      │      │                L2归一化，CPU推理，ROCm可选│
  │                      │      ├─ IndexService Faiss Flat 双索引：    │
  │                      │      │                检索→时间戳过滤→注册   │
  │                      │      └─ PostStore    帖子/向量/结果持久化    │
  │                      │           ▲  Protocol（接口）               │
  │                      │      ┌────┴───────────┐                    │
  │                      │  SqliteStore      (生产: MongoStore)        │
  └──────────────────────┴──────────────────────────────────────────┘
```

### 3.3 模块职责

| 模块 | 职责 | 关键选型 |
|---|---|---|
| API 层 | 收帖（校验→入队→202）、查结果 | FastAPI + Pydantic |
| 任务队列 | 解耦接收与计算 | 进程内 `asyncio.Queue`（有界，防内存膨胀） |
| Embedder | 图/文转向量并 L2 归一化；可注入协议接口（测试用 FakeEmbedder） | `open_clip` ViT-B/32 + `sentence-transformers` multilingual-e5-small；启动时加载一次常驻内存 |
| IndexService | 最大余弦相似度检索、向量注册、窗口过滤、压缩触发 | Faiss `IndexFlatIP` 双索引（图 512d / 文 384d） |
| PostStore | 数据访问协议：存帖元数据、存/读向量、读写 `index_status`、读写相似度结果 | Demo: SQLite(WAL)；生产: MongoDB（motor），同一 Protocol 两个实现 |

### 3.4 关键设计决定

**① 30 天窗口：检索过滤 + 惰性残留 + 按需压缩（不做每日全量重建）**

- Faiss Flat 不支持删除 → 检索取 Top-K 后按帖子时间戳过滤过期命中。
- 过期向量留在索引中为惰性数据，按 1 万帖/天 ≈ 35MB/天增长，数月不压缩无压力。
- 压缩仅在有需求时触发（惰性占比过高/内存预算/低峰例行）：只读库中已持久化的向量重新 add，不重新提特征，30 万帖约 1-3 分钟。
- 已废弃方案：每日全量重建。生产环境数据在 MongoDB 且需重新提特征（串行 ~10 小时 / 8 进程 ~1.5 小时），纯浪费，不成立。

**② 崩溃恢复：状态标记 + 启动回放 + 启动时从库重建索引**

- 每帖带 `index_status`（pending / indexed / failed）。
- Worker 每帖处理完立即持久化向量并标记 indexed（先落库，后注册索引）。
- 进程启动时从库中 indexed 帖子的存量向量**直接重建内存索引**（取消索引磁盘持久化文件）：索引是库数据的纯函数，天然幂等去重，消除"索引文件 vs 数据库"双写不一致。重建成本：Demo <1s；生产 30 万 ≈ 1-3 分钟（服务就绪前 `/health` 报 not ready）。
- 启动序列：先从库重建内存索引，再回放 30 天内 `pending` 的帖子补计算。

**③ 容量与性能基线（生产目标 30 万帖/窗口）**

| 指标 | 数值 |
|---|---|
| 索引内存（双索引合计） | ~1.0 GB（图 586MB + 文 439MB；每帖 3584B） |
| 单次查询（Flat 全扫，内存带宽绑定） | ~30-40 ms |
| 压缩耗时（读存量向量） | 1-3 分钟 |
| 处理吞吐 | 单 Worker ~10 帖/秒；业务峰值 ~2 帖/秒，余量充足 |

结论：Flat 在生产全量下够用，无需近似索引；IVF/HNSW 仅作为发帖量涨一个数量级后的备选，封装在 IndexService 内部，上层无感。

**④ Demo → 生产迁移边界（核心逻辑零改动）**

| 层 | Demo | 生产 |
|---|---|---|
| PostStore 实现 | SQLite | MongoDB（motor） |
| 图片来源 | image_url / image_base64 | 对象存储 URL + httpx 下载（Embedder 输入统一为 bytes） |
| 部署形态 | 单进程 | API 多副本；Worker 按 post_id 分片消费防重复索引 |

**⑤ 模型加载**：启动时加载一次常驻内存；加载失败则 fail-fast 拒绝启动。

**⑥ Worker 并发模型**：Demo 单 Worker 串行消费（瓶颈不在此）；特征提取为 CPU 密集同步操作，放入独立线程池执行，避免阻塞事件循环。

## 4. 数据流

### 4.1 正常路径时序

```
业务方              API层            Queue          Worker              PostStore        Faiss
  │ POST /posts ────▶│                │              │                    │               │
  │                  │ 校验+幂等检查 ──┼──────────────┼───写帖(pending)────▶│               │
  │◀── 202 Accepted ─│ 入队 ─────────▶│              │                    │               │
  │                  │                │──取任务─────▶│                    │               │
  │                  │                │              │ 下载图片→CLIP编码(512d)             │
  │                  │                │              │ 文本→e5编码(384d)                   │
  │                  │                │              │──写向量────────────▶│               │
  │                  │                │              │──检索Top-K(图/文)───┼──────────────▶│
  │                  │                │              │ 时间戳过滤+排除自身  │               │
  │                  │                │              │──写结果(indexed)───▶│               │
  │                  │                │              │──add向量注册────────┼──────────────▶│
  │ GET /{id}/sim ──▶│ 查结果 ──────────────────────▶│                    │               │
  │◀── 200 分数 ─────│                │              │                    │               │
```

**顺序铁律**：
1. 先落库向量，后注册索引——崩溃最坏只是索引缺条目，启动重建补齐，永不丢数据。
2. 先检索，后注册自身——否则匹配到自己；重试场景自身可能已在索引中，检索结果需排除自身 post_id。
3. 检索取 Top-K 后按时间戳过滤——保证 30 天窗口语义。

### 4.2 幂等

以业务方 `post_id` 为幂等键：重复提交不重新计算，返回当前状态。业务方重发"修改后的内容"必须换新 post_id（API 文档写明）。

### 4.3 失败与重试

| 失败点 | 策略 |
|---|---|
| 图片下载失败 | 指数退避重试 3 次（1s/4s/16s）；仍失败 → `failed(image_download_failed)`，不自动重入队 |
| 图片解码失败（损坏/格式不符） | 直接 `failed(image_decode_failed)`，不重试 |
| 文本为空 | Demo 必填，API 层 422 拒绝 |
| 有界队列满 | API 阻塞等待 ≤5s，超时仍返回 202（已以 pending 落库，兜底扫描捞回） |
| Worker 处理中途崩溃 | 停留 pending，启动回放或兜底扫描补处理 |

**兜底扫描（latch sweep）**：Worker 空闲时每 5 分钟（可配置）扫描 PostStore 中滞留 >10 分钟的 pending 帖子重新入队。与启动回放构成双保险：启动回放管"进程死"，兜底扫描管"任务丢"。

**failed 帖子不自动重试**（已确认）；仅 `/admin/replay` 手动触发时重置为 pending 重算。

### 4.4 结果查询三态

| 状态 | 响应 |
|---|---|
| pending | 202 + `{"status": "pending"}`，业务方轮询（建议 1-2s） |
| indexed | 200 + `{max_sim, sim_image, sim_text, matched_post_id, computed_at}` |
| failed | 200 + `{"status": "failed", "reason": "..."}` |

## 5. 相似度计算与阈值

### 5.1 向量生成

| 信号 | 模型 | 维度 | 实现要点 |
|---|---|---|---|
| 图片 | CLIP ViT-B/32（open_clip） | 512 | resize 224×224（模型内置预处理）；输出 L2 归一化 |
| 文字 | multilingual-e5-small | 384 | **必须带前缀**：库存旧帖 `"passage: "`，新帖查询 `"query: "`（不用前缀严重掉点）；超长截断 512 token |

两路向量 L2 归一化 → Faiss 内积即余弦相似度，值域 [-1,1]，对外输出截断到 [0,1]。

### 5.2 最大相似度计算

```
image_max = max( cos(新帖图向量, 旧帖图向量) )   # Top-K=16 候选，过滤后取最大
text_max  = max( cos(新帖文向量, 旧帖文向量) )
max_sim   = max(image_max, text_max)
```

- Top-K 取 16：为时间戳过滤和自排除留缓冲；过滤后候选为空 → 该信号记 0。
- 窗口为空（冷启动第一帖）→ 所有分数记 0。
- 落库 `sim_image`、`sim_text`、`matched_post_id`（取得 max_sim 的旧帖）——分信号分数供业务调参与排查。

### 5.3 阈值与分数语义

原始余弦相似度未经校准（绝对分值随内容分布漂移）。设计上分两层：

**系统只输出原始分**，阈值全部配置化，不在系统内硬编码业务决策。下游按分数带消费，默认建议值（可调）：

| 分数带 | 语义参考 |
|---|---|
| `max_sim ≥ 0.90` | 疑似重复帖，重度降权 |
| `0.75 ≤ max_sim < 0.90` | 疑似相似，轻度降权 |
| `< 0.75` | 不处理 |

经验起点（仅供初始配置）：CLIP 图片余弦 ~0.85-0.90 以上通常对应近重复/裁剪；e5 文字 ~0.85 以上通常对应同义改写。

**校准路径（Demo 验证期必做）**：用真实重复帖正例 + 随机非重复负例各数百条跑分数分布，据此定阈值。若分布需要可加 logistic 校准映射为"重复概率"，列为二期可选，不阻塞 Demo。

### 5.4 数值与存储约定

- 向量 float32 落库（每帖 ~3.5KB）；分数保留 4 位小数。
- 阈值、Top-K、扫描节奏统一收敛到单一配置文件，支持环境变量覆盖。

## 6. API 接口

全部 JSON 交互；FastAPI 自动提供 `/docs`。统一错误格式：`{"error": {"code": "...", "message": "..."}}`。

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/posts` | 提交新帖，触发相似度计算 |
| GET | `/posts/{post_id}/similarity` | 查询计算结果 |
| GET | `/health` | 健康检查 |
| POST | `/admin/replay` | 手动触发回放（`{"mode": "compact"}` 触发压缩） |

### 6.1 POST /posts

请求体：

```json
{
  "post_id": "biz_post_10086",      // 幂等键，1-128字符，必填
  "image_url": "https://.../a.jpg", // 与 image_base64 二选一，必填其一
  "image_base64": null,             // 无URL时的兜底通道
  "text": "今天天气不错，出片了"        // 必填，≤5000字符
}
```

- 图片约束：≤20MB，JPEG/PNG/WebP，下载后校验。
- 幂等：post_id 已存在 → 200 + 当前状态（不重新计算）。
- 成功：`202 Accepted` + `{"post_id": "...", "status": "pending"}`。
- 错误：422 参数校验失败；413 图片超限；503 服务不可用（模型未就绪等）。

### 6.2 GET /posts/{post_id}/similarity

| 情况 | 状态码 | 响应体 |
|---|---|---|
| 计算中 | 202 | `{"status": "pending"}` |
| 完成 | 200 | 见下 |
| 失败 | 200 | `{"status": "failed", "reason": "image_download_failed"}` |
| 未知 | 404 | 统一错误格式 |

完成态：

```json
{
  "status": "indexed",
  "max_sim": 0.9123,
  "sim_image": 0.9123,
  "sim_text": 0.6210,
  "matched_post_id": "biz_post_08823",
  "computed_at": "2026-08-23T10:15:30Z"
}
```

典型端到端延迟（提交→可查）≈ 0.5-2s。

### 6.3 GET /health 与 POST /admin/replay

- `/health` → `{"status": "ok", "models_loaded": true, "index_count": 15234, "queue_size": 3, "oldest_pending_seconds": 1.2, "failed_count": 0}`。启动重建索引期间报 not ready。
- `/admin/replay` → 手动触发 pending 回放（或 compact 模式压缩重建）。生产可挂鉴权，Demo 裸开。

### 6.4 边界约定

- 鉴权：Demo 内网直连不做鉴权，预留中间件挂载点。
- 超时：图片下载 30s 总超时。
- 并发：API 层 async；特征提取放独立线程池，避免阻塞事件循环。

## 7. 错误处理

### 7.1 一致性模型

**SQLite（PostStore）是唯一事实源，Faiss 索引是可随时重建的内存缓存。**

不变式：
1. 状态为 indexed 的帖子，库里必有其向量与结果。
2. 索引内容 = 库中所有 indexed 帖子的向量集合（含窗口外的惰性残留；30 天窗口由检索时的时间戳过滤强制，见 3.4①）。启动重建即一致，运行中 Worker 单线程追加保持。
3. 崩溃唯一损失 = 已出队但未落库向量的任务（仍为 pending，回放捞回），零数据丢失。

### 7.2 故障分类全景

| 故障 | 检测 | 处理 | 最终状态 |
|---|---|---|---|
| 图片下载失败 | httpx 异常 | 指数退避重试 3 次 | failed(image_download_failed) |
| 图片解码失败 | PIL 解码异常 | 不重试 | failed(image_decode_failed) |
| 图片超限 | API 层校验 | 拒绝，不入队 | 413 |
| 编码异常 | try/except | 不重试 | failed(encode_failed) |
| PostStore 写入失败 | 异常 | 日志告警，停留 pending，兜底扫描重捞 | 最终一致 |
| 任务出队后崩溃 | — | 启动回放 | 无损恢复 |
| 队列丢任务 | 兜底扫描（5 分钟） | 重新入队 | 最终一致 |
| 模型加载失败 | 启动检查 | fail-fast 拒绝启动 | 部署阻断 |

### 7.3 重放与并发防重

- 回放/兜底扫描按 post_id 操作，与幂等键一致。
- in-flight 集合：Worker 处理中的 post_id 登记在内存集合，兜底扫描跳过，防止慢任务被误判滞留而重复入队、同一向量重复 add。

### 7.4 可观测性

**分阶段耗时打点**（Demo 要求）：每帖处理完输出一条完整耗时日志：

```
post_id=biz_post_10086 phase=complete total=1423ms
  breakdown: download=812ms image_embed=385ms text_embed=21ms
             search=38ms persist=12ms faiss_add=2ms
```

- 打点覆盖：图片下载、图片向量化、文字向量化、Faiss 检索、结果落库、向量注册。
- 实现：轻量 StageTimer 上下文管理器（进程内计时）；任一步骤失败时输出已完成部分的耗时。
- total > 5s（默认，可配置）输出 WARNING。

其余：失败日志 `post_id + phase + reason`；`/health` 四指标（index_count、queue_size、oldest_pending_seconds、failed_count）；reason code 枚举化。

### 7.5 优雅停机

SIGTERM → 停止入队 → 等待当前帖处理完成（上限 30s）→ 退出。"先落库向量"保证强杀最坏停留 pending，下次启动补齐。

## 8. 测试策略

### 8.1 模型依赖处理

Embedder 为可注入协议接口，测试分两档：

| 档位 | Embedder | 用途 |
|---|---|---|
| FakeEmbedder | 确定性伪向量 | 单元/集成测试主力，毫秒级，进 CI |
| 真实模型 | 本地真模型 | 冒烟测试（`@pytest.mark.slow`，手动跑，不进 CI 门禁） |

Faiss 不 mock：测试直接用真 Faiss 灌小规模向量。

### 8.2 各层测试重点

- **单元**：Embedder 输出维度/范数/e5 前缀；IndexService 相似度正确性、窗口过滤、自排除、空索引；Store 幂等、状态机迁移、向量 BLOB 往返；max(图,文) 组合、分数截断。
- **API 层**（TestClient + FakeEmbedder）：422/413/404 边界、幂等、三态查询。
- **集成**（FakeEmbedder 端到端）：POST→Worker→可查；**崩溃恢复测试**：处理中强杀 → 重启 → pending 回放补齐、索引与库一致（不变式验收）。

### 8.3 关键场景清单

| # | 场景 | 断言 |
|---|---|---|
| 1 | 同图不同 post_id 提交两次 | 第二帖 sim_image ≈ 1.0，命中第一帖 |
| 2 | 相似文本 | sim_text 高，max_sim 取文字侧 |
| 3 | 旧帖超 30 天窗口 | 过滤后 sim = 0 |
| 4 | 积压时重复提交同 post_id | 幂等，不重复计算 |
| 5 | 图片下载 404 | 3 次重试后 failed，reason 正确 |
| 6 | 崩溃恢复 | 见 8.2 集成层 |

### 8.4 效果评估（Demo 核心交付，独立于代码测试）

1. 构建标注集：正例对（真实重复帖，必含裁剪样本）+ 负例对（随机配对），各数百条。
2. 裁剪鲁棒性专项：程序化生成裁剪/缩放/轻度调色变体，验证图片相似度保持率。
3. 产出：正负例分数分布 → 定 5.3 分数带阈值；AUC 作为方案有效性指标。
4. 性能基线：从耗时日志汇总 P50/P95 各阶段耗时。

### 8.5 工具链

pytest + pytest-asyncio + httpx（TestClient）+ Faker + tmp_path 隔离 SQLite。目录：`tests/unit`、`tests/api`、`tests/integration`、`eval/`。实现阶段遵循 TDD。

## 9. 假设与范围约束

- Demo 阶段每帖必填一张图；未来支持纯文字帖仅需 `image_*` 转可选 + 无图时退化为纯文字比较。
- 不做多图对多图比较（Demo 约定单图）；架构上 IndexService 检索接口不阻塞未来扩展。
- 相似度为检索型近似：窗口内精确（Flat 暴力检索），但仅覆盖已入库帖子；系统启动前/窗口外的帖子不参与比较。
- 本系统只输出分数，"是否降权、降多少"由下游推荐系统决策。
